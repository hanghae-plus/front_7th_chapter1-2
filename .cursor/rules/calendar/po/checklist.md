# PO Agent Checklists

User Story 작성 및 검증을 위한 체크리스트 모음입니다.

## Artifacts 저장 프로세스

모든 User Story 작성 완료 및 사용자 승인 후:

1. ✅ **저장 경로**: `.cursor/rules/calendar/artifacts/po/`
2. ✅ **파일명 규칙**:
   - User Story: `us###-[feature-name].md`
   - Epic: `epic###-[epic-name].md`
   - Technical Story: `ts###-[tech-task].md`
   - 버그 수정: `us###-bugfix-[bug-description].md` (Standard User Story 사용)
   - 기술 조사: `ts###-research-[topic].md` (Technical Story 사용)
3. ✅ **저장 확인 메시지**: 파일 경로와 함께 안내
4. ✅ **다음 단계 준비**: @test-architect 작업 요청

## 1. User Story 완성도 체크리스트

User Story가 완성되었는지 확인하는 기본 체크리스트입니다.

### 📋 Story 구조

- [ ] **User Story 형식**이 올바른가?
  - "As a [user], I want [goal], So that [benefit]" 형식
  - 세 가지 요소 모두 명확하게 작성됨
- [ ] **사용자 역할**이 구체적인가?
  - "사용자"보다는 "일정 관리를 하는 직장인" 등 구체적
  - 해당 기능을 실제로 사용할 페르소나가 명확
- [ ] **목표(Want)**가 구체적인가?
  - 모호한 표현 없음
  - 무엇을 달성하려는지 명확
- [ ] **비즈니스 가치(So that)**가 명확한가?
  - 왜 이 기능이 필요한지 이해 가능
  - 측정 가능한 가치 또는 효과 제시

### 📖 Description

- [ ] **상세 설명**이 충분한가?
  - 배경 및 맥락 포함
  - 기능의 필요성 설명
- [ ] **User Journey**가 구체적인가?
  - 사용자의 실제 사용 흐름 제시
  - 각 단계별 행동과 결과 명시
- [ ] **예시**가 포함되어 있는가?
  - 구체적인 사용 시나리오
  - 실제 데이터를 사용한 예시

### ✅ Acceptance Criteria

- [ ] **Given-When-Then 형식**을 사용했는가?
  - 초기 상태(Given) 명확
  - 사용자 행동(When) 명확
  - 예상 결과(Then) 명확
- [ ] **정상 케이스**를 포함하는가?
  - Happy path 시나리오 작성
- [ ] **엣지 케이스**를 포함하는가?
  - 경계값 테스트
  - 특수한 조건의 시나리오
- [ ] **에러 케이스**를 포함하는가?
  - 실패 시나리오
  - 에러 처리 방법 명시
- [ ] **모든 AC가 테스트 가능**한가?
  - 모호한 표현 없음
  - 명확한 확인 기준 제시

### 📝 Tasks

- [ ] **TDD 5단계**로 분해되었는가?
  - 🧪 Test Setup
  - 🔴 Red: Test First
  - 🟢 Green: Implementation
  - 🔵 Refactor
  - 📝 Documentation
- [ ] **각 Task가 구체적**한가?
  - 체크 가능한 작업 항목
  - 애매한 표현 없음
- [ ] **예상 소요 시간**이 명시되었는가?
  - Small/Medium/Large 표시
- [ ] **의존성**이 명시되었는가?
  - 선행 작업 표시
  - 순서 명확

### 📊 추정 및 우선순위

- [ ] **Story Points**가 할당되었는가?
  - 피보나치 수열 또는 티셔츠 사이즈
  - 추정 근거 제시
- [ ] **Priority**가 명시되었는가?
  - High/Medium/Low
  - 비즈니스 가치 기반

### 🔧 Technical Notes

- [ ] **기술 스택**이 명시되었는가?
  - React, MUI, Vitest, MSW 등
- [ ] **구현 고려사항**이 포함되었는가?
  - 제약사항, 주의사항
  - 성능, 보안 고려사항
- [ ] **데이터 모델**이 정의되었는가? (해당 시)
  - TypeScript 인터페이스
  - API 스키마

### 📚 Definition of Done

- [ ] **완료 기준**이 명확한가?
  - 체크 가능한 항목들
  - 테스트, 리뷰, 문서화 포함

## 2. INVEST 원칙 검증

좋은 User Story의 6가지 원칙을 검증합니다.

### I - Independent (독립적)

- [ ] 다른 Story와 **독립적**으로 개발 가능한가?
- [ ] 특정 순서 없이 구현 가능한가?
- [ ] 다른 Story의 완료를 기다릴 필요가 없는가?

**만약 의존성이 있다면**:

- [ ] 의존성이 명시되어 있는가?
- [ ] 의존성을 제거할 수 있는가?
- [ ] Story 분할을 재고려했는가?

### N - Negotiable (협상 가능)

- [ ] **구현 방법**이 유연한가?
- [ ] What(무엇)에 집중하고 How(어떻게)는 열려있는가?
- [ ] 개발자가 최선의 구현 방법을 선택할 여지가 있는가?

**피해야 할 것**:

- [ ] 구현 세부사항을 과도하게 명시하지 않았는가?
- [ ] 특정 기술이나 패턴을 강제하지 않는가?

### V - Valuable (가치 있는)

- [ ] **사용자에게 명확한 가치**를 제공하는가?
- [ ] "So that" 부분이 구체적인가?
- [ ] 비즈니스 목표와 연결되는가?

**가치 검증**:

- [ ] 이 기능이 없다면 어떤 문제가 발생하는가?
- [ ] 이 기능으로 사용자가 얻는 이점은 무엇인가?
- [ ] ROI(투자 대비 효과)가 긍정적인가?

### E - Estimable (추정 가능)

- [ ] **복잡도를 추정**할 수 있는가?
- [ ] Story가 충분히 명확한가?
- [ ] 기술적 불확실성이 없는가?

**추정 불가능한 경우**:

- [ ] Spike(조사 작업)가 필요한가?
- [ ] 명세를 더 구체화할 필요가 있는가?
- [ ] Story를 더 작게 분할할 필요가 있는가?

### S - Small (작은)

- [ ] **한 스프린트 내 완료** 가능한가?
- [ ] 1-2주 내에 개발 가능한가?
- [ ] 너무 크거나 작지 않은가?

**적절한 크기**:

- [ ] Story Points: 1-13 범위 (피보나치)
- [ ] 13 이상이면 Epic으로 분할 고려
- [ ] 1 미만이면 Task로 처리 고려

**분할이 필요한 신호**:

- [ ] Task가 20개 이상인가?
- [ ] 여러 스프린트가 필요한가?
- [ ] 여러 개발자가 동시에 작업해야 하는가?

### T - Testable (테스트 가능)

- [ ] **Acceptance Criteria가 테스트 가능**한가?
- [ ] 완료 여부를 명확히 판단할 수 있는가?
- [ ] 자동화 테스트로 검증 가능한가?

**테스트 가능성 확인**:

- [ ] Given-When-Then으로 작성되었는가?
- [ ] 정량적 기준이 있는가? (예: "3초 이내", "100자 이하")
- [ ] 모호한 표현이 없는가? (예: "빠르게", "적절하게")

## 3. Task 분해 체크리스트 (TDD 기반)

Task를 TDD 방법론에 맞게 분해했는지 검증합니다.

### 🧪 Phase 1: Test Setup

- [ ] **MSW 핸들러** 정의가 포함되었는가?
  - [ ] Express API 엔드포인트 mock
  - [ ] 성공 시나리오 (200, 201)
  - [ ] 클라이언트 에러 (400, 404)
  - [ ] 서버 에러 (500)
  - [ ] 네트워크 에러
- [ ] **Mock 데이터** 생성이 포함되었는가?
  - [ ] API 응답 형식 mock 데이터
  - [ ] 정상 케이스 데이터
  - [ ] 엣지 케이스 데이터
  - [ ] 에러 응답 데이터
- [ ] **Test 유틸리티** 작성이 포함되었는가?
  - [ ] 커스텀 렌더 함수
  - [ ] 공통 setup 함수
  - [ ] Helper 함수

### 🔴 Phase 2: Red - Test First

- [ ] **Unit Test** 작성이 포함되었는가?
  - [ ] 컴포넌트 렌더링 테스트
  - [ ] Props 전달 테스트
  - [ ] State 변경 테스트
  - [ ] 함수 로직 테스트
- [ ] **Integration Test** 작성이 포함되었는가?
  - [ ] 컴포넌트 간 상호작용
  - [ ] API 호출 및 응답 처리
  - [ ] 에러 핸들링
  - [ ] 로딩 상태
- [ ] **User Interaction Test** 작성이 포함되었는가?
  - [ ] 클릭/입력 이벤트
  - [ ] 폼 제출
  - [ ] 유효성 검증

**테스트 작성 원칙 확인**:

- [ ] 테스트가 먼저 작성되는가? (Red 단계)
- [ ] 테스트가 실패하는 것을 확인하는가?
- [ ] 한 번에 하나의 테스트만 작성하는가?

### 🟢 Phase 3: Green - Implementation

- [ ] **Component 구현**이 포함되었는가?
  - [ ] 기본 구조 생성
  - [ ] Props 인터페이스 정의
  - [ ] State 관리
  - [ ] Event 핸들러
- [ ] **비즈니스 로직 구현**이 포함되었는가?
  - [ ] 핵심 함수 구현
  - [ ] 데이터 변환/가공
  - [ ] 유효성 검증
- [ ] **API 연동**이 포함되었는가?
  - [ ] Express API 호출 함수
  - [ ] 응답 데이터 처리
  - [ ] 에러 핸들링
  - [ ] 로딩 상태 관리
  - [ ] 재시도 로직 (필요 시)
- [ ] **UI 연결**이 포함되었는가?
  - [ ] MUI 컴포넌트 연동
  - [ ] 스타일링
  - [ ] 반응형 처리

**구현 원칙 확인**:

- [ ] 최소한의 코드로 테스트를 통과시키는가?
- [ ] 테스트 통과 후 다음 단계로 진행하는가?
- [ ] 구현하지 않은 기능은 테스트도 없는가?

### 🔵 Phase 4: Refactor

- [ ] **코드 정리**가 포함되었는가?
  - [ ] 중복 코드 제거
  - [ ] 함수 분리 (단일 책임)
  - [ ] 상수화
  - [ ] 타입 강화
- [ ] **성능 최적화**가 포함되었는가?
  - [ ] useMemo, useCallback
  - [ ] 컴포넌트 분리
  - [ ] 디바운싱/쓰로틀링
- [ ] **재사용성 향상**이 포함되었는가?
  - [ ] 커스텀 훅 추출
  - [ ] 공통 컴포넌트화
  - [ ] 유틸리티 분리

**리팩토링 원칙 확인**:

- [ ] 테스트가 여전히 통과하는가?
- [ ] 기능은 변경하지 않고 구조만 개선하는가?
- [ ] 리팩토링 후 모든 테스트를 실행하는가?

### 📝 Phase 5: Documentation

- [ ] **코드 문서화**가 포함되었는가?
  - [ ] JSDoc 주석
  - [ ] 복잡한 로직 설명
  - [ ] 사용 예시
- [ ] **프로젝트 문서화**가 포함되었는가?
  - [ ] README 업데이트
  - [ ] CHANGELOG 작성
  - [ ] API 문서 (해당 시)
- [ ] **테스트 문서화**가 포함되었는가?
  - [ ] 테스트 케이스 설명
  - [ ] 커버리지 리포트

### Task 분해 품질 검증

- [ ] 각 Phase의 **의존성**이 명확한가?
- [ ] 각 Task의 **예상 소요 시간**이 합리적인가?
- [ ] Task가 **너무 크지 않은가**? (1일 이내 완료 가능)
- [ ] Task가 **너무 작지 않은가**? (최소 30분 이상)
- [ ] **병렬 처리** 가능한 Task가 있는가?

## 4. Acceptance Criteria 품질 체크리스트

Acceptance Criteria의 품질을 검증합니다.

### 📋 형식 검증

- [ ] **Given-When-Then 형식**을 사용했는가?
  - [ ] Given: 전제 조건/초기 상태
  - [ ] When: 사용자 행동/트리거
  - [ ] Then: 예상 결과/시스템 반응
- [ ] **명확한 구분**이 되어 있는가?
  - [ ] 각 단계가 명확히 분리됨
  - [ ] And로 추가 조건 명시

### 🎯 완전성 검증

- [ ] **정상 케이스**를 포함하는가?
  - [ ] Happy path 시나리오
  - [ ] 가장 일반적인 사용 케이스
- [ ] **엣지 케이스**를 포함하는가?
  - [ ] 경계값 (최소/최대)
  - [ ] 빈 값/null/undefined
  - [ ] 특수 문자
  - [ ] 매우 긴 입력
  - [ ] 동시성 이슈
- [ ] **에러 케이스**를 포함하는가?
  - [ ] 유효성 검증 실패
  - [ ] 네트워크 에러
  - [ ] 권한 부족 (해당 시)
  - [ ] 타임아웃
  - [ ] 서버 에러

### ✅ 테스트 가능성 검증

- [ ] **측정 가능한가?**
  - [ ] 정량적 기준 (숫자, 시간)
  - [ ] 구체적인 값
- [ ] **관찰 가능한가?**
  - [ ] UI에서 확인 가능
  - [ ] 로그로 확인 가능
  - [ ] 상태 변화 확인 가능
- [ ] **자동화 가능한가?**
  - [ ] Testing Library로 테스트 가능
  - [ ] 수동 개입 없이 검증 가능

### 🚫 피해야 할 표현

- [ ] 모호한 표현이 **없는가**?
  - ❌ "빠르게", "적절하게", "충분히"
  - ✅ "3초 이내", "최소 8자 이상", "100자 이하"
- [ ] 주관적 표현이 **없는가**?
  - ❌ "보기 좋게", "사용자 친화적으로"
  - ✅ "버튼이 파란색", "에러 메시지 표시"
- [ ] 불필요한 구현 세부사항이 **없는가**?
  - ❌ "useState를 사용하여", "Redux에 저장"
  - ✅ "입력값이 저장됨", "상태가 유지됨"

### 📊 일관성 검증

- [ ] **용어**가 일관적인가?
  - [ ] product-glossary.md의 용어 사용
  - [ ] 같은 개념은 같은 단어로
- [ ] **형식**이 일관적인가?
  - [ ] 모든 AC가 동일한 형식
  - [ ] 들여쓰기와 구조 통일

## 5. React + TDD 프로젝트 체크리스트

React와 TDD 방법론에 특화된 체크리스트입니다.

### ⚛️ React 고려사항

#### Component 설계

- [ ] **컴포넌트가 적절히 분리**되었는가?
  - [ ] 단일 책임 원칙 준수
  - [ ] 재사용 가능한 구조
- [ ] **Props 인터페이스가 명확**한가?
  - [ ] TypeScript interface 정의
  - [ ] 필수/선택 props 구분
  - [ ] 기본값 설정
- [ ] **State 관리가 명확**한가?
  - [ ] Local state vs Global state 구분
  - [ ] 상태 끌어올리기 고려
  - [ ] 불필요한 리렌더링 방지

#### Hooks 활용

- [ ] **적절한 Hook** 사용인가?
  - [ ] useState: 간단한 상태
  - [ ] useReducer: 복잡한 상태 로직
  - [ ] useEffect: 사이드 이펙트
  - [ ] useMemo/useCallback: 성능 최적화
- [ ] **Custom Hook** 추출이 고려되었는가?
  - [ ] 재사용 가능한 로직
  - [ ] 복잡한 상태 로직 캡슐화

#### MUI 컴포넌트 (기구현됨)

- [ ] **기존 MUI 컴포넌트 활용**이 명시되었는가?
  - [ ] 일정 관리 앱에 이미 구현된 UI
  - [ ] 필요 시 기존 컴포넌트 재사용
- [ ] **데이터 연결**이 명시되었는가?
  - [ ] Props 전달

## 체크리스트 활용 가이드

### 순차적 검증 프로세스

1. **User Story 완성도 체크리스트** (필수)
2. **INVEST 원칙 검증** (필수)
3. **Task 분해 체크리스트** (필수)
4. **Acceptance Criteria 품질 체크리스트** (필수)
5. **React + TDD 프로젝트 체크리스트** (기술 스택 관련)
6. **일정 관리 앱 도메인 체크리스트** (도메인 관련)
7. **품질 기준 최종 체크** (최종 검증)

### 체크리스트 우선순위

#### 🔴 High Priority (필수)

- User Story 완성도
- INVEST 원칙
- Task 분해
- Acceptance Criteria 품질
- 품질 기준 최종 체크

#### 🟡 Medium Priority (권장)

- React + TDD 프로젝트 체크리스트
- 일정 관리 앱 도메인 체크리스트

#### 🟢 Low Priority (선택)

- 추가 최적화 항목
- Nice-to-have 기능

### 체크리스트 실패 시 대응

- **50% 미만 통과**: Story 재작성 필요
- **50-80% 통과**: 부족한 부분 보완
- **80% 이상 통과**: 최종 검토 후 승인 요청
