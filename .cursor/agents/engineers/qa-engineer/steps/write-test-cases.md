# Step: 통합 테스트 케이스 문서 작성

````xml
<step>
  <purpose>
    정의한 시나리오를 바탕으로 통합 테스트 케이스 문서를 작성합니다.
    실제 테스트 코드는 작성하지 않고, Test First Engineer가 코드를 작성할 수 있도록 충분히 상세한 문서를 작성합니다.
  </purpose>

  <how-to>
    <action n="1">
      <do>테스트 케이스 문서 구조 생성</do>
      <detail>
        테스트 케이스 문서는 다음 구조로 작성합니다:

        ```markdown
        # 테스트 케이스: {{기능명}}

        ## 통합 테스트 시나리오

        ### 시나리오 1: {{시나리오 제목}}
        **목적**: {{테스트 목적}}

        **전제 조건**:
        - {{전제 조건 1}}
        - {{전제 조건 2}}

        **테스트 단계**:
        1. {{단계 1}}
        2. {{단계 2}}
        ...

        **기대 결과**:
        - {{기대 결과 1}}
        - {{기대 결과 2}}

        **참고 파일**: src/__tests__/medium.integration.spec.tsx

        ---

        ## 유닛 테스트 작성 시 고려사항

        Test First Engineer가 유닛 테스트를 작성할 때 다음 사항을 고려해주세요:

        ### 필요한 유닛 테스트
        1. **{{함수명 1}}**
           - {{테스트 케이스 1}}
           - {{테스트 케이스 2}}

        ### 경계값 테스트 케이스
        - {{경계값 케이스 1}}
        - {{경계값 케이스 2}}

        ### 테스트 데이터 예시
        \```
        // {{케이스 설명}}
        { input: '...', expected: '...' }
        \```
        ```

        파일 위치: `docs/testcases/{{기능명}}-testcases.md`
      </detail>
    </action>

    <action n="2">
      <do>통합 테스트 시나리오 작성</do>
      <detail>
        사용자 시나리오 기반의 통합 테스트를 문서로 작성합니다:

        작성 원칙:
        1. **시나리오 제목**: "사용자가 ~할 수 있다" 형식
        2. **목적**: 이 테스트가 검증하려는 것을 명확히 작성
        3. **전제 조건**: 테스트 시작 전 필요한 상태
        4. **테스트 단계**: 사용자가 수행하는 동작을 순서대로 나열
        5. **기대 결과**: 각 단계 후 기대되는 결과

        예시:
        ```markdown
        ### 시나리오 1: 사용자가 반복 일정을 생성할 수 있다
        **목적**: 사용자가 UI를 통해 반복 일정을 생성하고 캘린더에 표시되는지 확인

        **전제 조건**:
        - 사용자가 로그인되어 있음
        - 캘린더 페이지가 열려 있음

        **테스트 단계**:
        1. '일정 추가' 버튼 클릭
        2. 제목 입력: '매일 회의'
        3. '반복' 체크박스 선택
        4. 반복 유형 선택: 'daily'
        5. 시작일 선택: '2025-01-01'
        6. 종료일 선택: '2025-01-07'
        7. '저장' 버튼 클릭

        **기대 결과**:
        - 캘린더에 '매일 회의' 일정이 7일간 표시됨
        - 각 날짜에 일정이 정확히 표시됨
        - 성공 메시지가 표시됨

        **참고 파일**: src/__tests__/medium.integration.spec.tsx
        ```

        주의사항:
        - 테스트 단계는 구체적으로 작성 (버튼 이름, 입력 값 등)
        - Test First Engineer가 코드로 변환할 수 있을 정도로 상세하게
        - 사용자 관점에서 작성 (구현 세부사항 X)
      </detail>
    </action>

    <action n="3">
      <do>경계값 및 예외 케이스 시나리오 추가</do>
      <detail>
        정상 케이스뿐만 아니라 경계값과 예외 케이스도 시나리오로 작성합니다:

        예시:
        ```markdown
        ### 시나리오 2: 매월 31일 반복 시 31일이 없는 달은 건너뛴다.
        **목적**: 매월 31일 반복 일정이 31일이 없는 달(2월, 4월 등)을 올바르게 처리하는지 확인

        **전제 조건**:
        - 사용자가 로그인되어 있음
        - 캘린더 페이지가 열려 있음

        **테스트 단계**:
        1. '일정 추가' 버튼 클릭
        2. 제목 입력: '월말 정산'
        3. '반복' 체크박스 선택
        4. 반복 유형 선택: 'monthly'
        5. 시작일 선택: '2025-01-31'
        6. 종료일 선택: '2025-04-30'
        7. 반복 날짜: 31일
        8. '저장' 버튼 클릭

        **기대 결과**:
        - 1월 31일에 일정 표시됨
        - 2월에는 일정이 표시되지 않음 (2월은 31일이 없음)
        - 3월 31일에 일정 표시됨
        - 4월에는 일정이 표시되지 않음 (4월은 31일이 없음)

        **경계값 케이스**:
        - 윤년 2월 29일 반복
        - 매월 1일 반복 (모든 달에 존재)
        - 매월 30일 반복 (2월 제외)
        ```

        경계값 케이스 작성 원칙:
        - PRD에 명시된 예외 규칙을 모두 포함
        - 최소값, 최대값, 경계값 테스트
        - 예외 상황 (에러 케이스) 포함
      </detail>
    </action>

    <action n="4">
      <do>유닛 테스트 작성 가이드 작성</do>
      <detail>
        Test First Engineer가 유닛 테스트를 작성할 때 참고할 가이드를 작성합니다:

        작성 내용:
        1. **필요한 유닛 테스트 목록**
           - 함수/모듈별로 필요한 테스트 나열
           - 각 함수가 검증해야 할 케이스 명시

        2. **경계값 테스트 케이스**
           - 구체적인 경계값 케이스 나열
           - 각 케이스의 기대 동작 설명

        3. **테스트 데이터 예시**
           - 실제 테스트에 사용할 입력/출력 예시
           - 코드 블록으로 작성하여 복사 가능하게

        예시:
        ```markdown
        ## 유닛 테스트 작성 시 고려사항

        Test First Engineer가 유닛 테스트를 작성할 때 다음 사항을 고려해주세요:

        ### 필요한 유닛 테스트
        1. **generateRecurringDates 함수**
           - 매일 반복 로직
           - 매주 반복 로직
           - 매월 반복 로직 (31일 규칙 포함)
           - 매년 반복 로직 (윤년 2/29 규칙 포함)

        2. **validateRecurringConfig 함수**
           - 유효한 반복 설정 검증
           - 잘못된 날짜 범위 검증
           - 필수 필드 누락 검증

        ### 경계값 테스트 케이스
        - 매월 31일 반복 → 31일이 없는 달 처리
        - 윤년 2월 29일 반복 → 평년 처리
        - 시작일 = 종료일
        - 시작일 > 종료일 (에러 케이스)
        - interval = 0 또는 음수 (에러 케이스)

        ### 테스트 데이터 예시
        \```
        // 매일 반복
        { type: 'daily', startDate: '2025-01-01', endDate: '2025-01-07', interval: 1 }
        예상 결과: 7개 날짜

        // 매월 31일 반복
        { type: 'monthly', startDate: '2025-01-31', endDate: '2025-04-30', interval: 1, dayOfMonth: 31 }
        예상 결과: 2개 날짜 (1월 31일, 3월 31일)

        // 윤년 2월 29일
        { type: 'yearly', startDate: '2024-02-29', endDate: '2028-02-29', interval: 1 }
        예상 결과: 2개 날짜 (2024-02-29, 2028-02-29)
        \```
        ```

        주의사항:
        - 함수 인터페이스 설계는 Test First Engineer가 담당
        - 여기서는 어떤 함수가 필요한지만 제안
        - 테스트 데이터는 구체적으로 작성
      </detail>
    </action>

    <action n="5">
      <do>문서 검증 및 완성도 확인</do>
      <detail>
        작성한 테스트 케이스 문서가 충분히 상세한지 확인합니다:

        체크리스트:
        1. **통합 테스트 시나리오**
           - [ ] 모든 수용 기준이 시나리오로 작성됨
           - [ ] 각 시나리오의 목적이 명확함
           - [ ] 테스트 단계가 구체적임 (버튼 이름, 입력 값 등)
           - [ ] 기대 결과가 명확함
           - [ ] 경계값 케이스가 포함됨

        2. **유닛 테스트 가이드**
           - [ ] 필요한 함수/모듈 목록이 작성됨
           - [ ] 각 함수의 테스트 케이스가 나열됨
           - [ ] 경계값 케이스가 구체적임
           - [ ] 테스트 데이터 예시가 포함됨

        3. **Test First Engineer가 코드 작성 가능한가?**
           - [ ] 통합 테스트 시나리오를 코드로 변환할 수 있는가?
           - [ ] 유닛 테스트를 설계할 충분한 정보가 있는가?
           - [ ] 경계값 케이스를 코드로 작성할 수 있는가?

        나쁜 예시:
        ```markdown
        ### 시나리오 1: 반복 일정 생성
        - 일정을 생성한다
        - 반복 설정을 한다
        - 저장한다
        ```
        → 너무 간략함, 구체적인 동작이 없음

        좋은 예시:
        ```markdown
        ### 시나리오 1: 사용자가 반복 일정을 생성할 수 있다
        **테스트 단계**:
        1. '일정 추가' 버튼 클릭
        2. 제목 입력: '매일 회의'
        3. '반복' 체크박스 선택
        4. 반복 유형 선택: 'daily'
        5. 시작일 선택: '2025-01-01'
        6. 종료일 선택: '2025-01-07'
        7. '저장' 버튼 클릭
        ```
        → 구체적인 동작과 값이 명시됨
      </detail>
    </action>
  </how-to>

  <constraints>
    <constraint>테스트 케이스는 문서 형태로 작성할 것 (코드 X)</constraint>
    <constraint>통합 테스트 시나리오는 사용자 관점에서 작성할 것</constraint>
    <constraint>테스트 단계는 구체적으로 작성할 것 (버튼 이름, 입력 값 등)</constraint>
    <constraint>유닛 테스트 가이드는 Test First Engineer가 참고할 수 있도록 상세하게 작성할 것</constraint>
    <constraint>모든 수용 기준이 시나리오로 작성되어야 함</constraint>
    <constraint>경계값 케이스가 포함되어야 함</constraint>
  </constraints>

  <success-criteria>
    <criterion>테스트 케이스 문서가 생성됨 (docs/testcases/{{기능명}}-testcases.md)</criterion>
    <criterion>모든 수용 기준이 통합 테스트 시나리오로 작성됨</criterion>
    <criterion>경계값 케이스가 포함됨</criterion>
    <criterion>유닛 테스트 작성 가이드가 포함됨</criterion>
    <criterion>Test First Engineer가 코드를 작성할 수 있을 정도로 상세함</criterion>
  </success-criteria>
</step>
````
